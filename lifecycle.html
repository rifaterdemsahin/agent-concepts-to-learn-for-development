🔄 Systems Life Cycle of AI Agents

__main__ assert — spec, build, test, deploy, monitor, iterate; telemetry feeds new requirements in a closed continuous improvement loop.

📊 INFOGRAPHIC: Continuous Agentic Life Cycle Spec → CI → Telemetry → Iteration
🎯 1. Executable Spec

Requirements live as machine-readable constraints rather than static documentation decks.

🧪 2. CI-Gated Acceptance

assert run() ensures agents pass integration tests deterministically before deployment.

📡 3. Monitoring & Re-feeding

Production rejection patterns and edge cases feed straight back into the specification dictionary.

Why an agent project still needs a life cycle

It is tempting to treat an LLM demo as magic glue. It is not. The grocery bot is a small system with the same stages as any other:

Test: the spec as an assertion

if __name__ == "__main__":
    print("tools:", [t["name"] for t in mcp_handle({"method": "tools/list"})["tools"]])
    assert run(), "acceptance test failed: bot never reached done_when"
    print("acceptance test passed ->", SPEC["done_when"])

This is a tiny acceptance test:

  • Given the SPEC and the mocked environment,
  • When the agent loop runs (bounded),
  • Then it must reach done_when (order_placed).

Because mock_llm is deterministic, this is also a regression test. Break the validator, drop the error feedback, or remove tool routing and the assert fails.

Monitor: traces are requirements in disguise

Every step prints something useful: 

[0] tool list_pantry -> {...}
[1] REJECTED: basket £10.70 is below minimum £50
[2] ORDER OK -> {'status': 'order_placed', 'total': 50.6}
[3] DONE
acceptance test passed -> order_placed

In production those lines are your telemetry. Patterns that become the next SPEC entry:

  • Repeated identical rejections → the prompt is missing the rule the validator enforces.
  • Unknown-item errors → tool schema or catalog data is incomplete.
  • Hitting max_steps often → goal is underspecified or tools are insufficient.
  • Long, expensive histories → need summarisation or a tighter budget in tokens().

Iterate: close the loop back to Spec

The dashed edge on the diagram is the important one. Monitoring does not end the project; it feeds requirements.

Example: logs show 40% of runs reject for “too many lines” when users order bulky weeks. That is not a model bug — it is a missing requirement. Add max_lines: 24 (or a bulk mode) to SPEC, let the validator and the prompt pick it up, and keep the same assert as the bar.

Exercise 4 in the README is this stage in miniature: add per-step logging, write one new requirement from what you see.

Exercises

  1. Break one gate (comment out the min-basket check). Does the assert still pass? Should it?
  2. Add structured logging (json.dumps per step) suitable for a log aggregator.
  3. Write a second assert for “never more than N rejections”. That is a quality requirement made executable.
  4. List three signals you would monitor if this bot ran daily in a kitchen. What SPEC field would each one produce?
