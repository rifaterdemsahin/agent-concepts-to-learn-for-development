Understanding requirements

SPEC becomes the prompt, the validator rules, and the acceptance test — one source of truth, three consumers.

What “requirements” means here

In agent work the requirements are not a slide deck — they are a small, executable object. In poc/bot.py that object is the SPEC dict on the [REQ] section: 

SPEC = {"goal": "restock low items", "min_basket_gbp": 50, "max_lines": 12,
        "low_stock_below": 2, "done_when": "order_placed"}

Each field has a job beyond documentation. If a rule only lives in prose, the model will ignore it and the test will not notice. If it lives in SPEC, every stage of the harness can read the same number.

Field by field

FieldValueBecomes
goal restock low items Part of the prompt. The model is told what “good” looks like before it invents a goal.
min_basket_gbp 50 A validate() rule. Also the reason the first basket is rejected (it is under £50).
max_lines 12 Another validator rule. Caps how large a single order can grow.
low_stock_below 2 Domain rule the model should use when choosing what to restock. It is in the prompt the model sees.
done_when order_placed The acceptance criterion. assert run() only passes when the loop reaches that state.

How the SPEC travels

1 · Into the prompt

The first message in run() is the whole dict, serialised as JSON: 

msgs = [{"role": "user", "content": json.dumps(SPEC)}]   # spec becomes the prompt

The model never hears “please make a basket of at least fifty pounds unless you feel like it”. It hears the same object the validator uses. Prompt and code stay aligned by construction.

2 · Into the validator

validate() does not invent thresholds. It reads them: 

if basket_total(b) < SPEC["min_basket_gbp"]:
    return f"basket £{basket_total(b)} is below minimum £{SPEC['min_basket_gbp']}"

That message is not a crash — it is structured feedback the loop appends as an error role, so the model can correct itself on the next step.

3 · Into the acceptance test

The life-cycle gate at the bottom of the file is one assert: 

assert run(), "acceptance test failed: bot never reached done_when"

run() returns True only when the model emits an action that ends the task (done_when). If the bot never places an order, the process exits non-zero. The requirement is therefore not just stated — it is CI-enforced.

Why one source of truth

Design rule: if a constraint matters, put it in SPEC and reference it. Prose can explain it. Code must execute it.
  • Change is cheap. Raising the minimum to £80 is one edit; the prompt, the rejection message, and the test all follow.
  • Feedback is honest. The error text quotes the same number the model was told, so retries are convergent, not confusing.
  • Tests are not a second spec. Acceptance is “did you meet done_when?”, not a parallel checklist that drifts.

Walkthrough with the grocery bot

  1. run() seeds history with json.dumps(SPEC).
  2. The model returns a basket that totals about £10.70 — under min_basket_gbp.
  3. validate() returns basket £10.70 is below minimum £50.
  4. The loop prints REJECTED, appends an error message, and continues.
  5. The model retries with a larger basket. Validator passes. Order is placed.
  6. assert run() passes because done_when was reached.

Exercises

  1. Change min_basket_gbp to 80. Run the bot. What happens at max_steps?
  2. Add a max_basket_gbp field to SPEC, teach validate() to enforce it, and mention it in the prompt (the prompt is just the dict — nothing else to edit).
  3. Rename done_when to finished everywhere it is read. Notice how few places need to change when the spec is the hub.
