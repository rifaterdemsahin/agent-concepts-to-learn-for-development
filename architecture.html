Agent architecture

run() loop: calls the LLM, gates output, routes tools — a bounded harness around a stateless model.

The agent is the loop, not the model

A raw LLM is a text-in / text-out function. An agent is a control loop that keeps calling that function, interpreting its output, acting on the world (via tools), and feeding results back. In poc/bot.py that loop is run(). 

def run(max_steps=8):
    msgs = [{"role": "user", "content": json.dumps(SPEC)}]  # spec becomes the prompt
    for step in range(max_steps):                           # bounded loop = safety
        raw = mock_llm(msgs)
        ...

Four responsibilities of the harness

1 · Call the LLM

Each step starts with one model call over the full history. The harness owns msgs; the model does not persist anything between calls. See LLM fundamentals.

2 · Gate the output

Before anything is trusted: 

try: out = parse(raw)
except ValueError as e:
    msgs.append({"role": "error", "content": str(e)}); continue
err = validate(out)
if err:
    print(f"[{step}] REJECTED: {err}")
    msgs.append({"role": "error", "content": err}); continue

Two gates: can we extract a JSON object, and does that object obey SPEC? Failure is not fatal — it is new context for the next step. Details in Output handling.

3 · Route tools

Once an action is valid, the harness decides what to do with it:

  • "tool" → mcp_handle({"method": "tools/call", ...})
  • "order" → same MCP path, with the place_order tool
  • "done" → return True (the acceptance state)

The model never touches the pantry directly. All side effects go through one interface. See MCP dev.

4 · Bound the loop

max_steps=8 is a safety property. An agent that can retry forever is a hang risk and a cost risk. If the model never reaches done_when, run() returns False and the acceptance assert fails.

Message roles are the protocol

RoleWho appends itMeaning
userharness (once)The SPEC — the task
assistant (implied raw)modelFree-text proposal (JSON or prose + fences)
toolharnessObservation from mcp_handle
errorharnessParse or validate failure — ask the model to fix it

This tiny vocabulary is enough. The model learns the contract from the history the harness builds.

Why this shape

Separation of concerns: the model proposes; the harness disposes. Requirements live in SPEC, world state lives behind MCP, memory lives in msgs, and control lives in run(). Swap any one without rewriting the others.
  • Testable. mock_llm makes the loop deterministic. Swap in a real API and the gates stay identical.
  • Safe by default. Unparsed or rule-breaking output cannot reach tools.
  • Observable. Every rejection and tool call is printed — raw material for the monitor stage.

Walkthrough of one successful run

  1. Step 0 — model sees SPEC, returns {"action":"tool","name":"list_pantry",...}.
  2. Harness routes tools/call; pantry JSON is appended as a tool message.
  3. Step 1 — model proposes a basket. It is under £50. validate rejects; error is appended.
  4. Step 2 — model proposes a larger basket. Validator passes. place_order runs.
  5. Step 3 — model returns {"action":"done", ...}. Loop returns True.

Exercises

  1. Log every step index and action. Which step is most often the rejection? Why?
  2. Add a third action type "ask" that returns a clarifying question. What should the harness do with it?
  3. Remove the max_steps bound and give the mock model a permanent bug. What does that teach you?
