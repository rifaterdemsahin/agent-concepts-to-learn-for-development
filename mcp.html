MCP dev

mcp_handle() — tools/list and tools/call give the loop a standard tool interface.

What MCP is for

The Model Context Protocol (and this PoC’s simplified mirror of it) answers a practical question: how does an agent use tools without hard-coding every tool into the loop?

Two methods are enough to teach the idea:

  1. tools/list — what can you do? Returns names, descriptions, input schemas.
  2. tools/call — do this, with these arguments. Returns content the harness can observe.

The registry

TOOLS = {
 "list_pantry": {"description": "Current stock per item", "inputSchema": {"type": "object"},
                 "fn": lambda a: PANTRY},
 "place_order": {"description": "Order {item: qty}", "inputSchema": {"type": "object"},
                 "fn": lambda a: {"status": "order_placed", "total": basket_total(a["basket"])}},
}

Each entry is declarative metadata plus an implementation. The model only ever needs the metadata; the harness only ever calls fn.

mcp_handle()

def mcp_handle(req):
    if req["method"] == "tools/list":
        return {"tools": [{"name": n, **{k: v for k, v in t.items() if k != "fn"}} for n, t in TOOLS.items()]}
    t = TOOLS[req["params"]["name"]]
    return {"content": t["fn"](req["params"]["arguments"])}

Note what it does on tools/list: it strips fn. Implementation stays server-side. The client (the agent loop) learns names and schemas, never Python callables.

Standard message shape

Discover

mcp_handle({"method": "tools/list"})

→ {"tools": [{name, description, inputSchema}, …]}

Invoke

mcp_handle({
  "method": "tools/call",
  "params": {
    "name": "list_pantry",
    "arguments": {}
  }
})

→ {"content": {...}}

How the loop uses it

When a validated action is tool or order, the harness builds that same JSON-shaped request: 

res = mcp_handle({"method": "tools/call",
                  "params": {"name": out["name"], "arguments": out["arguments"]}})
msgs.append({"role": "tool", "content": json.dumps(res["content"])})

Two consequences:

  • The model proposes intent (tool name + args), never raw side effects.
  • Tool results re-enter as observations — the same free-text discipline as model output, but produced by code.

Why a standard interface

Stable seam: tools can grow (prices, delivery slots, coupons) without changing run(). The loop only knows two verbs: list and call.
  • Swappable servers. Today an in-process dict; tomorrow a subprocess or HTTP server — same request shape.
  • Model-friendly. tools/list is exactly what you paste into a system prompt or a tool-calling API field.
  • Safe surface. Only registered tools run. A hallucinated tool name simply misses the registry.

Schemas matter

inputSchema is the contract for arguments. In production MCP this is JSON Schema; here it is a placeholder. Either way the lesson is the same: declare what a tool accepts so the model can form valid calls and the server can reject invalid ones.

Compare with output handling: model text is validated against SPEC; tool arguments would be validated against the schema. Same pattern at both boundaries.

Walkthrough

  1. __main__ prints tools/list → ['list_pantry', 'place_order'].
  2. Model asks for list_pantry. Harness calls tools/call. Pantry JSON goes into msgs.
  3. Model emits an order. Harness routes place_order via the same handler.
  4. Handler returns {"status":"order_placed","total":…}. Loop continues to done.
