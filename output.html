Output handling

parse(), validate() — first basket is under £50, rejected, error fed back, model retries.

Free text is not an API

Even a well-prompted model returns a string. In this PoC the mock is deliberately messy once: 

return "Sure!\n```json\n" + json.dumps({"action": "order", "basket": bad}) + "\n```"

So the first job is extraction, not interpretation.

parse() — extract a JSON object

def parse(text):
    m = re.search(r"\{.*\}", text, re.S)
    if not m: raise ValueError("no JSON found")
    return json.loads(m.group(0))

It pulls the first brace-delimited block and loads it. Failure raises; the loop turns that into an error message and continues. Nothing unstructured reaches tools.

Production note: real systems often want a schema, repair passes, or constrained decoding. The principle stays the same — treat model text as untrusted input at a system boundary.

validate() — enforce the spec

def validate(out):
    if out["action"] == "order":
        b = out["basket"]
        if not set(b) <= set(PRICE): return "unknown item"
        if len(b) > SPEC["max_lines"]: return "too many lines"
        if basket_total(b) < SPEC["min_basket_gbp"]:
            return f"basket £{basket_total(b)} is below minimum £{SPEC['min_basket_gbp']}"
    return None

Three rules, two of them read from SPEC. The function returns a string on failure (human-readable, quotable) or None on success. That string becomes model context.

The reject → retry story

StepModel outputValidatorHarness response
1 {"action":"tool","name":"list_pantry"} pass (no basket) Call tool; append pantry JSON as tool.
2 Basket {milk:2, yoghurt:2, rice:1} ≈ £10.70 fail Print REJECTED; append error; continue.
3 Basket {milk:6, yoghurt:6, rice:4, eggs:6} pass Place order; append receipt as tool.
4 {"action":"done"} pass return True — acceptance reached.

Walk the numbers for the accepted basket: {milk: 6, yoghurt: 6, rice: 4, eggs: 6} = 6×1.5 + 6×2.0 + 4×3.2 + 6×2.8 = 9 + 12 + 12.8 + 16.8 = £50.60. That clears min_basket_gbp (50). The first attempt fails for the same reason the third passes: the threshold lives in SPEC and is checked every time.

Why feed the error back?

Two options when output is invalid: retry silently (same input, same output — infinite loop), or write the failure into history. The second is the agent pattern: 

msgs.append({"role": "error", "content": err}); continue

On the next call the model sees what was wrong in the same message list as the original task. That is why the mock’s error branch can finally succeed — the context changed.

Gates in the loop

try: out = parse(raw)
except ValueError as e:
    msgs.append({"role": "error", "content": str(e)}); continue
err = validate(out)
if err:
    print(f"[{step}] REJECTED: {err}")
    msgs.append({"role": "error", "content": err}); continue

Order matters: parse before validate. You cannot check a basket you have not extracted. Both failures are recoverable; only the step budget and a valid done end the loop.

Principles

  • Untrusted input. Free text is a boundary crossing — validate like any user input.
  • Errors as data. A precise rejection is more useful than a traceback; the model can fix it.
  • Spec-driven rules. Thresholds live in SPEC, not magic numbers in the validator.
  • Idempotent retries. Nothing side-effecting runs until validation passes.

Exercises

  1. Print basket_total(b) on every reject. Confirm the £50 story.
  2. Make the mock return prose with no JSON on one step. Watch parse feed an error and the next step recover.
  3. Change the error text format. Does the mock still recover? What does that say about real model prompting?
  4. Move min_basket_gbp out of SPEC into a local constant. Which link in the chain from requirements breaks?
